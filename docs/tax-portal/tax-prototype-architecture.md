# Tax prototype architecture

Two applications, both generated from Nava Strata templates with
`bin/new-app` and styled with the Colorado Design System.

```text
 Taxpayer (phone)          Examiner
       │                      │
       ▼                      ▼
 ┌──────────────────────────────────────┐        ┌────────────────────────┐
 │ tax-portal (Rails + Strata SDK)      │  HTTP  │ tax-engine (Flask)     │
 │  taxpayer portal   examiner portal   │ ─────▶ │  POST /v1/returns/     │
 │  interview flow    tasks, cases      │        │        calculate       │
 │  business process, audit log         │ ◀───── │  PolicyEngine US       │
 └──────────────────────────────────────┘ lines  └────────────────────────┘
                  │ Postgres
```

## tax-engine

`POST /v1/returns/calculate` takes what the taxpayer told us (people, ages,
filing status, income by type, withholding) and returns each line of the
Colorado return with the facts and the source behind it, plus the refund or
amount owed. `src/tax/calculator.py` is the only code that knows about
PolicyEngine; replacing it with another calculator would not change the API.
Responses include the engine name and version, which the portal stores with
every calculation.

### Running and sizing the engine

Measured on a 4-core development machine:

- Loading the tax rules takes about a minute and 2 to 3 GB of memory per
  process. That is two sets of rules: 2025, and 2027 with the graduated
  rates. The 2025 rules alone took about 30 seconds and 1.5 GB.
- A new calculation takes about half a second of one CPU core. One process
  handles a little over one new calculation a second, however many requests
  arrive at once. Repeating the same facts is answered from memory.
- Three processes handled about three to five calculations a second.
  (Measured with the 2025 rules only, when they used about 4 GB together.)

So the production server (`tax-engine/gunicorn.conf.py`) runs one worker per
container, and capacity is added by running more containers. Each container
is given 1 vCPU and 4 GB in `infra/tax-engine/app-config/<env>.tf`.
`TAX_ENGINE_PRELOAD=true` loads the rules when the container starts.

### Connecting the portal to the engine when deployed

| Setting | Where it comes from |
| --- | --- |
| Engine `API_AUTH_TOKEN` | Generated by the engine's service layer and kept in the parameter store at `/tax-engine-<env>/service/api-auth-token` |
| Portal `TAX_ENGINE_API_TOKEN` | Reads that same parameter |
| Portal `TAX_ENGINE_URL` | A parameter you create by hand at `/tax-portal-<env>/service/tax-engine-url` once the engine's address is known |

Order for a new environment: deploy `tax-engine`, create the URL parameter,
then deploy `tax-portal`. A deployed portal refuses to start a calculation
without both settings; only local development falls back to the engine that
`bin/demo` starts.

Not yet tested: none of this has been deployed. The Terraform is formatted
and follows the template's variables, but it has not been planned or applied
against an AWS account.

### How a return is processed

```text
file_return ─submitted─▶ calculate_return ─▶ screen_return ─┬─cleared─▶ finalize_return ─▶ end
 (taxpayer)                 (system)           (system)     └─flagged─▶ review_return ─┬─approved──────────────▶ finalize_return
                                                                          (examiner)  └─information requested─▶ provide_information
                                                                              ▲                                    (taxpayer)
                                                                              └──────────── information provided ───────┘
```

Filing only records the return and queues `ProcessReturnJob`. The taxpayer
gets a confirmation number straight away and their status page shows
"Received", then updates on its own. The job calculates the return, runs
the checks and, when nothing is flagged, accepts it, usually within a second
or two.

The case is the record of what is left to do: a case still at
`calculate_return` has not been processed. If the job fails or is lost (the
tax engine is down, a container is replaced), nothing is lost and the
taxpayer is not asked to file again. `bin/rails tax:process_pending` picks
those cases up; in AWS it runs every five minutes (see
`infra/tax-portal/app-config/env-config/scheduled_jobs.tf`).

Pages a person is waiting on give the engine 10 seconds; background
processing gives it 60. If the engine doesn't answer, the checklist shows
without its estimate.

Not yet done: jobs run inside the web process. That is enough with the
scheduled sweep behind it, but a production service should run them in
separate workers with a durable queue.

The automatic checks are in `app/services/return_processing/screen.rb`:
income lower or withholding higher than the payer reported, a record on file
the taxpayer disputes, withholding with no record on file, a dependent
claimed on another return, and a refund that is large for the income.

A filed return is never edited. An examiner's change is a
`ReturnAdjustment`; the case keeps both the filed and the adjusted
calculation.

Controls on examiners (`app/services/return_processing/examiner_actions.rb`):

- Only the examiner a return is assigned to can act on it. Taking a return
  over from someone else is allowed and is written to the history.
- A change of $500 or more to what the taxpayer receives, and any decision
  not to accept a return, goes to a `second_review` step. A different
  examiner confirms it or sends it back with a note; the examiner who
  proposed it can't confirm it. The $500 is illustrative, not policy.
- A return that isn't accepted closes with the outcome `not_accepted` and a
  reason the taxpayer sees. The prototype can't reopen it for correction.

### Data protection

- SSNs and bank account numbers use Active Record encryption
  (`config/initializers/active_record_encryption.rb`). Deployed environments
  must supply the keys as secrets.
- Pundit policies: taxpayers reach only their own return
  (`TaxReturnPolicy`); only examiners reach `/staff` (`StaffPolicy`).
- Amounts and personal data are not written to application logs or audit
  line data.
- Demo sign-in exists only when `DEMO_MODE=true` and never in production.

## Demo copies

In demo mode each visitor gets a private copy of the demo people
(`DemoSpace`, `tax-portal/app/models/demo_space.rb`). The first time a
browser chooses a person, `DemoSpace.start!` creates all seven people, their
records on file and their returns, and a signed cookie ties the browser to
that copy. `users` and `wage_records` carry a `demo_space_id`; everything
else belongs to a copy through its user.

- Anything that reads across people is limited to the signed-in person's
  copy through `DemoMode.cases_for` and `DemoMode.tasks_for`: the examiner
  dashboard, lists, work queue, "pick up next" and measures, records on
  file, and the check for a dependent claimed on another return.
- People who are not demo people have no copy and see only data that
  belongs to no copy, so nothing changes outside demo mode.
- A copy is discarded when its visitor chooses **Start the demo over**, or
  after two hours without use (checked when the visitor returns and when
  the next visitor starts). `bin/rails tax:demo_reset` discards them all.
- Demo people stay signed in for as long as their copy lasts.

## Keeping a hosted demo fast

Measured with `bin/serve` on a 4-core test machine:

| Step | Cold | Warmed up | With a database 15 ms away |
| --- | --- | --- | --- |
| Most pages | 0.06 to 0.1 s | the same | 0.2 to 0.35 s |
| First "Continue as …" after a start | 8 s | 1.1 s | |
| "Continue as …" after that | 0.3 to 0.9 s | 0.3 s | about 4 s |
| "New rates" page, first time | 10 s | 0.1 s | |

- The tax engine's first calculations after a start are slow, and it
  remembers each household. `bin/rails tax:demo_warm` (`DemoWarmup`) runs
  the demo households through it once, in a copy that is then discarded.
  `bin/serve`, `docker-compose.yml` and `render.yaml` run it at start.
- Creating a visitor's copy makes about 245 database calls, most of them
  the normal filing and processing of three returns. With the database on
  the same machine that costs a quarter of a second. `bin/serve` can run
  its own Postgres (`SERVE_DATABASE=local`, the default on Replit).
- `/demo/diagnostics` (`DemoDiagnostics`) times the database, the engine
  and a new calculation on a running demo.
